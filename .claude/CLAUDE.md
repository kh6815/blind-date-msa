# CLAUDE.md

## 작업 원칙

### 0. 초기화 설정
- md파일은 마크다운 문법을 적용하여 사용한다.
- 주석은 제외하고 실행한다.

### 1. 코드를 작성하기 전에 먼저 생각하기

추측하지 않는다. 혼란을 숨기지 않는다. 선택의 근거와 대안을 드러낸다.

- 가정한 내용이 있다면 명확하게 설명한다.
- 확실하지 않다면 질문한다.
- 여러 해석이 가능하다면 모두 제시하고, 임의로 하나를 선택하지 않는다.
- 요구사항이 불명확하다면 구현을 멈추고 무엇이 불명확한지 설명한 뒤 질문한다.

### 2. 단순함 우선, 요청 범위 내에서만

문제를 해결하는 최소한의 코드만 작성한다. 사용자가 요청하지 않은 것은 하지 않는다.

**작성하지 않는 코드**
- 요청하지 않은 기능, 미래를 대비한 추상화
- 세 번째 중복 전까지는 공통화하지 않는다
- 요청되지 않은 확장성 및 설정 기능
- 실제로 발생하지 않는 상황을 위한 과도한 예외 처리

**하지 않는 작업**
- 기능 추가, 리팩터링, 의존성 추가
- 코드 스타일 변경, 대규모 구조 변경
- 테스트 생략, 코드 내용을 반복 설명하는 주석 작성

> 이 코드를 시니어 개발자가 봤을 때 과하다고 느끼지 않을까?

그렇다면 더 단순하게 작성한다.

### 3. 수정 범위 최소화

기존 코드를 수정할 때:

- 요청과 관련 없는 코드 수정, 리팩터링, 포맷팅 변경 금지
- 기존 프로젝트 스타일을 따른다
- 관련 없는 문제를 발견했다면 언급만 하고 수정하지 않는다
- 주석을 제거하지 않는다
- 내가 만든 unused import / 변수 / 메서드만 제거한다. 원래부터 존재하던 불필요한 코드는 요청이 없다면 제거하지 않는다

모든 변경 라인은 사용자의 요청과 직접적으로 연결될 수 있어야 한다.

### 4. 검증 가능한 목표 정의

"동작하게 만들기"가 아니라 "검증 가능한 목표"를 정의한다.

- **유효성 검증 추가**: 잘못된 입력 테스트 작성 → 실패 확인 → 코드 수정 → 통과 확인
- **버그 수정**: 버그 재현 테스트 작성 → 실패 확인 → 코드 수정 → 통과 확인
- **리팩터링**: 기존 테스트 통과 확인 → 리팩터링 → 재실행, 결과 동일 확인

### 5. 여러 단계 작업 시 계획 먼저 제시

```
1. 결제 검증 로직 분석       → 기존 동작 확인
2. 실패 케이스 테스트 작성   → 테스트 실패 확인
3. 서비스 로직 수정          → 테스트 통과 확인
4. 전체 영향도 검증          → 기존 테스트 재실행
```

각 단계는 반드시 검증 가능한 기준을 포함해야 한다.

### 6. 코드 품질 기준

- 읽기 쉬움이 영리함보다 중요하다
- 주니어 개발자가 30초 안에 이해할 수 있어야 한다
- 함수는 가능한 짧게, 하나의 역할만 수행한다
- 주석보다 의미 있는 이름을 사용한다
- 새로운 패턴을 만들기보다 기존 프로젝트 패턴을 따른다

### 7. 테스트 실행 범위

수정/구현한 기능에 대해 빌드 및 테스트가 필요한 경우:

- 해당 기능과 관련된 테스트가 이미 있는지 먼저 확인한다.
- 없다면 관련 테스트를 새로 작성한다.
- 검증은 수정한 내용과 직접 관련된 테스트만 실행한다. (`./gradlew test --tests "FullyQualifiedClassName"`)
- 전체 테스트(`./gradlew test`)나 관련 없는 테스트코드는 실행하지 않는다.

## 작업 완료 후 문서화 절차

### 목적

프로젝트 문서는 개발자가 빠르게 시스템을 이해하고 유지보수할 수 있도록 돕기 위해 존재한다. 단순 구현 내용이나 일회성 작업은 문서화하지 않는다.

### 1. docs 문서화 필요 여부 판단

다음 중 하나라도 YES라면 문서화를 검토한다.

- **3개월 뒤 다시 참고할 가능성이 있는가?** (예: 인증 구조, Redis 사용 방식, 파일 업로드 처리, 신청서/결제/배치 처리 흐름)
- **프로젝트의 핵심 규칙 또는 패턴인가?** (예: SubmitStep 패턴, 인증 처리 방식, 예외 처리 규칙, 분산 락, 트랜잭션 처리)
- **동일한 설명을 미래에 반복하게 될 가능성이 있는가?** (예: 구현 이유, 특정 제약사항, 업무 규칙, 운영 시 주의사항)

모두 NO라면 문서화하지 않는다. (단순 버그 수정, 변수명 변경, 메서드 분리, 코드 정리, 포맷팅, 테스트 추가, 일회성 운영 대응 등)

### 2. 기존 문서 우선 원칙

새 문서를 생성하기 전에 반드시 기존 문서를 먼저 검토한다.

1. 기존 문서에 추가 가능한가?
2. 기존 문서에 포함하는 것이 더 자연스러운가?
3. 기존 문서로 설명하기 어려운가?

새 문서는 다음 조건을 **모두** 만족할 때만 생성한다: 독립된 주제 / 의미 있는 분량 / 향후 반복 참고 가능성 / 기존 문서에 포함하기 어려움

### 3. 문서 작성 형식

```markdown
# 제목

## 목적
## 사용 위치
## 동작 방식
## 주요 규칙
## 주의사항
## 관련 코드
```

좋은 문서는 **왜 존재하는지 / 언제 사용하는지 / 어떤 제약이 있는지 / 무엇을 주의해야 하는지 / 관련 코드가 어디에 있는지**를 설명한다. 코드만 읽어도 알 수 있는 내용은 문서화하지 않는다.

> 불필요한 문서보다 없는 문서가 낫다. 문서는 양보다 유지보수 가치가 중요하다.

### 4. 문서 작성 규칙
1. 문서를 작성할 때 보안 적인 부분은 제외하고 작성한다(ex. 비밀번호, IP 등))

### 작업 완료 체크리스트

- 요청 범위 내에서만 수정했는가
- 테스트를 수행하고 결과를 확인했는가
- project.md 갱신 여부를 확인했는가
- 기존 문서 업데이트 가능성을 먼저 검토했는가
- 필요한 경우 docs 문서를 작성했는가
